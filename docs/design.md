# Sound Scraper: Design v0.2

Desktop app that records whatever the computer is playing (system audio loopback) to MP3, with a library for renaming recordings and editing ID3 tags. Targets macOS and Windows first, Linux later.

## 1. Stack (decided by Alex, 2026-10-03)

**A Rust core, with a native UI built in React Native for Windows (`react-native-windows`) and macOS (`react-native-macos`).**

Goals: write the app logic once, use native UI controls, and keep the door open for Linux.

```
┌──────────────── React Native UI (TypeScript, shared) ────────────────┐
│  RecordBar · SourcePicker · LibraryTable · TagEditor · Settings      │
└──────────────────────────────┬───────────────────────────────────────┘
                               │  JS calls / events (JSI)
┌──────────────────────────────▼───────────────────────────────────────┐
│  SoundScraperModule: thin per-OS native module over the C header     │
│  macOS: Objective-C++ · Windows: C++/WinRT (both wrap sound_scraper.h)│
└──────────────────────────────┬───────────────────────────────────────┘
                               │  C ABI (header generated by cbindgen)
┌──────────────────────────────▼───────────────────────────────────────┐
│  Rust core (crate `sound_scraper_core`, staticlib)                   │
│  recorder state machine · LAME encoder · library/SQLite · rename · ID3│
│  └─ capture backends: windows.rs (WASAPI) · macos.rs (taps / SCK)    │
│                       linux.rs (PipeWire, later)                     │
└──────────────────────────────────────────────────────────────────────┘
```

Where each kind of code lives:
- **All app logic is in Rust and shared:** recording states, encoding, finalize/recover, the library index, rename, and tags. It is unit-tested on its own with no UI.
- **Platform-specific code** exists only in the capture backends (Rust), the build/packaging projects, and small OS calls such as permission prompts and "Show in Finder/Explorer". Those go through the core's C API where possible.
- **Bridge (Alex's proven approach):** cbindgen produces the C ABI header, and each OS gets a thin generated native module that exposes it to React Native: Objective-C++ on macOS and C++/WinRT on Windows. These modules only marshal arguments; there is no logic in them. A shared TS module spec keeps the two in sync.
- **The C ABI is the stable seam.** It is opaque handles and plain structs, plus a callback for events: state changes, elapsed time, levels, and "app closed". cbindgen generates `sound_scraper.h`, and the Rust build produces a static library that each native project links.

Native-UI notes:
- RN macOS renders real AppKit views. RN Windows with the New Architecture renders through Windows Composition, styled to Fluent. Controls RN doesn't cover, such as a native table or the file picker, are added as small native components or modules.
- `react-native-macos` usually trails core React Native by a release, so we pin RN versions to match it.

**Linux path (deferred, not closed):** the Rust core and its C ABI are already portable, so Linux needs only a UI. There are two options:
1. A React Native GTK platform (a new open-source project rendering RN components with GTK4 widgets, similar to RN Windows/macOS). It reuses all TypeScript UI code but is a large undertaking.
2. A small native GTK4 UI in Rust (gtk-rs / Relm4) calling the core directly. It is quicker, but the UI is written a second time.
The choice can wait. Nothing in the core depends on React Native.

Alternatives considered: Tauri (web UI rather than native controls, so ruled out), Flutter (ruled out), Qt (native-ish, all three OSes, but C++/QML UI and licensing).

## 2. Audio capture per platform

A `CaptureBackend` trait hides the platform:

```rust
trait CaptureBackend {
    fn list_outputs() -> Vec<OutputDevice>;          // device picker
    fn start(device: Option<DeviceId>, sink: Sender<AudioChunk>) -> Result<Session>;
    fn stop(session: Session);
}
// AudioChunk = interleaved f32 PCM + sample_rate + channels
```

**Windows: WASAPI loopback.** Open the render (output) device in shared mode with `AUDCLNT_STREAMFLAGS_LOOPBACK`. Works on Windows 7+, no permissions prompt. Via the `cpal` crate (supports loopback on output devices) or the `windows` crate directly if we need finer control. Note: WASAPI loopback delivers no packets during silence, so the backend inserts silence based on elapsed time to keep the timeline correct.

**macOS: Core Audio process taps (macOS 14.2+), ScreenCaptureKit fallback (macOS 13+).**
- Default: `AudioHardwareCreateProcessTap` with a global tap on all processes, wrapped in a private aggregate device. Audio-only, no screen-recording semantics. Requires the "System Audio Recording" permission (`NSAudioCaptureUsageDescription`).
- Fallback for macOS 13 to 14.1: ScreenCaptureKit `SCStream` with `capturesAudio = true` and a minimal video config. Requires Screen Recording permission, which is a scarier prompt for users.
- Below macOS 13: unsupported (would need a virtual driver like BlackHole). Minimum OS: macOS 13.
- Bindings via `objc2` / `objc2-core-audio` / `screencapturekit` crates.

**Linux (later):** PipeWire or PulseAudio monitor source of the default sink. Per-app capture works there too, by linking a single app's PipeWire node.

### Capture source: all system audio or one app

Before recording, the user picks a **Source**: "All system audio" (the default) or one specific app. The trait takes a source:

```rust
enum CaptureSource { System { device: Option<DeviceId> }, App { app: AppTarget } }
struct AppTarget { pid: u32, bundle_id: Option<String>, name: String, icon: Option<Vec<u8>> }
fn list_audio_apps() -> Vec<AppTarget>;   // fills the app picker
```

**The app picker** lists running apps, with the ones currently playing sound sorted to the top (each marked with a small speaker icon). It refreshes while open.
- macOS: `kAudioHardwarePropertyProcessObjectList` with `kAudioProcessPropertyIsRunningOutput`, mapped to apps through `NSRunningApplication`.
- Windows: audio sessions from `IAudioSessionManager2`, plus the list of running windowed apps.

**Per-app capture on Windows** uses process loopback. It calls `ActivateAudioInterfaceAsync` with `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` and `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`, so child processes are included (browsers play audio from helper processes). This needs Windows 10 build 20348 or later, which in practice means Windows 11. On older Windows the app option is greyed out with an explanation, and system capture still works.

**Per-app capture on macOS:**
- Taps (macOS 14.2+): create a `CATapDescription` that lists the app's process objects (`kAudioHardwarePropertyTranslatePIDToProcessObject`). It also includes helper processes whose bundle ID starts with the app's bundle ID, so Chrome and Safari renderers are captured.
- ScreenCaptureKit fallback (macOS 13): an `SCContentFilter` that includes only that `SCRunningApplication`.

**Edge cases:**
- If the target app quits mid-recording, recording continues as silence, and the UI says "App closed". If an app with the same bundle ID or executable relaunches, it is re-attached automatically.
- The source cannot be changed while recording or paused; stop first. (Switching sources mid-file is a possible later feature.)
- The chosen source is saved as a default, matched by bundle ID or executable path, not by PID.
- The recording's default name includes the source, e.g. `Spotify 2026-10-03 14-05.mp3`, and the app name is written to the ID3 comment.

**Microphone:** deferred. The pipeline is a single source for now, but the encoder input is a mixer node, so a mic can be added later without restructuring.

## 3. Recording model: start / pause / stop

State machine, owned by the Rust core:

```
Idle --start--> Recording --pause--> Paused --resume--> Recording
Recording/Paused --stop--> Finalizing --> Idle
```

- **Start:** create `Recordings/<timestamp>.mp3.part`, open the capture session, start the encoder thread. Audio flows `capture -> ring buffer -> resample/downmix if needed -> LAME encoder -> file`.
- **Pause:** keep the file and encoder open; the capture stream is stopped (or its chunks dropped) so nothing is written. Resuming appends seamlessly; the gap is simply absent from the file. Elapsed time in the UI excludes paused time.
- **Stop:** flush the encoder (`lame_encode_flush`), write the LAME/Xing header so players show the correct duration and can seek, write initial ID3 tags (title = default name, date, "Sound Scraper" as encoder), rename `.part` to `.mp3`, add it to the library.
- **Crash safety:** a leftover `.part` file on startup is offered for recovery (flush what's there, write tags, rename). Because MP3 is frame-based, a truncated file is still playable.
- One recording at a time in v1. Global hotkeys and a tray/menu-bar control are nice-to-haves.

## 4. MP3 encoding

- Encoder: **LAME** via the `mp3lame-encoder` crate. LAME is LGPL, so we link it dynamically (or ship it as a separate lib) to keep the app's own license free; noted for the licensing review.
- Default: **192 kbps CBR, 44.1 or 48 kHz (matches the device), stereo**. CBR keeps duration math and seeking simple. Settings offer 128/192/256/320 CBR and VBR V0/V2.
- Device formats are usually f32 at 48 kHz; LAME accepts that rate natively, so resampling only happens for unusual rates (via `rubato`). Multichannel (5.1) is downmixed to stereo.
- Encoding runs on its own thread with a bounded queue so a slow disk never blocks the audio callback.

## 5. Library view

- Source of truth is the **recordings folder** (default `~/Music/Sound Scraper`, changeable in settings). A small SQLite index (`library.db`) caches duration, size, and tags for fast listing; it is rebuilt from the folder if missing, and a file watcher picks up external changes.
- Table columns: Name, Duration, Date recorded, Size, Artist/Album (from tags). Sort, search filter, built-in play/preview, "Show in Finder/Explorer", delete (to trash).
- **Rename:** inline edit of the name. Renames the file on disk (sanitized for illegal characters, collision gets " (2)"), and by default also updates the ID3 Title if it still matched the old name. Rename of the file currently recording is disabled.

## 6. ID3 tag editing

- Library: the `id3` crate. Write **ID3v2.4** (with an ID3v2.3 option for older players), plus no v1 tag by default.
- Editable fields: Title, Artist, Album, Album artist, Year/Date, Track #, Genre, Comment, Cover art (pick an image, embedded as APIC).
- Edit panel opens from the library row (side panel). Multi-select allows bulk editing of shared fields (e.g. set Album on ten files).
- Writes go to a temp copy then atomically replace the original so a crash never corrupts a recording.

## 7. Repository structure

```
core/                    Rust workspace
  crates/core/           recorder, encoder, library, tags, C API (ffi.rs)
  crates/capture/        CaptureBackend + windows.rs, macos_tap.rs, macos_sck.rs
  include/sound_scraper.h  (generated by cbindgen)
app/                     React Native app (TypeScript)
  src/                   RecordBar, SourcePicker, LibraryTable, TagEditor, Settings
  src/native/            NativeSoundScraper.ts (shared module spec)
  windows/               RN Windows solution + C++/WinRT module, links core.lib
  macos/                 RN macOS Xcode project + Obj-C++ module, links libcore.a
```

The UI subscribes to core events through the module (state, elapsed time, input level at about 10 Hz).

## 8. Packaging and permissions

- macOS: signed and notarized `.dmg`; `NSAudioCaptureUsageDescription` in Info.plist; first-run screen explains the permission and links to System Settings if denied.
- Windows: signed MSI/NSIS installer; no special permissions.
- Auto-update (later): Sparkle on macOS, and MSIX/App Installer or WinSparkle on Windows.
